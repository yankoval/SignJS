# SignJS — Инструмент для создания ЭЦП (CAdES-BES)

Простое и надежное веб-приложение для формирования электронной подписи локальных файлов через браузер. Проект разработан для упрощения работы с системой **«Честный ЗНАК»** (ГИС МТ) и другими сервисами, требующими формат подписи PKCS#7 (CAdES-BES).

## Основные возможности
- **Два режима подписи:** - **Отсоединенная (Detached):** Создается файл `.sig`, содержащий только криптографический хвост (идеально для ГИС МТ).
  - **Встроенная (Attached):** Исходный файл упаковывается внутрь подписи.
- **Умный поиск сертификатов:** Скрипт проверяет как личное хранилище пользователя (`Current User`), так и хранилище компьютера (`Local Machine`).
- **Безопасность:** Файлы не загружаются на сервер. Вся криптография выполняется локально через расширение КриптоПро.

## Архитектура облачной обработки

Каждый сервер с запущенным SignJS обслуживает только свою часть организаций. Соответствие ИНН сертификатам хранится локально на сервере и определяет его зону ответственности. Нельзя предполагать, что на всех серверах установлен одинаковый набор сертификатов.

Из этого следуют обязательные правила обработки сообщений YMQ:

- сервер подписывает сообщение только тогда, когда для ИНН настроен локальный сертификат;
- отсутствие локальной настройки или сертификата означает «организация не обслуживается этим сервером», а не «сообщение ошибочно»;
- сервер без подходящего сертификата не должен вызывать `DeleteMessage`: сообщение может быть предназначено другому серверу;
- сообщение удаляется из очереди только сервером, который успешно сформировал и загрузил подпись;
- организация, для которой подпись глобально отключена, должна иметь отдельный явный статус. Этот статус нельзя определять по отсутствию сертификата на одном из серверов;
- некорректные и глобально необрабатываемые сообщения должны направляться в отдельный карантин или DLQ по общей политике, а не удаляться отдельным сервером как неизвестные ему.

### Требование к маршрутизации

Одна общая очередь с конкурирующими потребителями не гарантирует, что сообщение получит сервер с нужным сертификатом. Поэтому целевая схема должна маршрутизировать сообщения по ИНН или по идентификатору сервера: например, через отдельные очереди для серверов либо через центральный диспетчер, знающий распределение организаций.

До реализации такой маршрутизации обработчик, получивший сообщение для чужой организации, обязан сохранить его для повторной доставки и не считать успешно обработанным. При этом следует применять контролируемую задержку повторной доставки, чтобы чужие сообщения не создавали постоянный цикл получения и не занимали всю очередь.

### Сохранение состояния мониторинга

Облачный обработчик запоминает последнее состояние, явно выбранное пользователем:

- после нажатия «ВКЛЮЧИТЬ МОНИТОРИНГ» состояние сохраняется как включённое;
- после нажатия «ОСТАНОВИТЬ» состояние сохраняется как выключенное;
- при первом открытии страницы мониторинг выключен;
- при последующей загрузке или обновлении страницы восстанавливается последнее сохранённое состояние;
- автоматическая остановка из-за ошибки конфигурации не изменяет сохранённый пользовательский выбор.

Состояние хранится в `localStorage` для профиля браузера и origin (схема, хост, порт), а не для конкретной страницы или пути. Вкладки одного origin используют общий выбор пользователя. Он не синхронизируется между серверами, браузерами, разными профилями и режимами инкогнито.

### Одна ведущая вкладка (начиная с 1.3.0)

- Все обновлённые вкладки и same-origin iframe запрашивают эксклюзивную блокировку Web Locks `signjs-cloud-monitor`. Только её владелец читает YMQ, подписывает, загружает подпись и удаляет сообщения.
- Остальные вкладки показывают «Режим наблюдения» и состояние/анимацию лидера через `BroadcastChannel`. По каналу передаются только команды синхронизации и категории состояния — без API-ключей, сертификатов, документов, подписанных URL и receipt handles.
- «Включить» и «Остановить» в любой вкладке изменяют общий сохранённый выбор. Наблюдатель не запускает собственный polling. Изменять настройки API и ИНН следует при остановленном мониторинге; перед новым захватом лидерства настройки перечитываются.
- После закрытия или ухода с ведущей страницы следующая готовая вкладка получает блокировку. Вкладка, возвращённая из back/forward cache, заново участвует в выборе лидера. Вкладка без готового КриптоПро может наблюдать, но не становится лидером.
- Остановка прекращает новый polling. Полученная после остановки партия остаётся для повторной доставки без подписи. Уже начатая подпись/загрузка завершается с удержанием блокировки до конца операции; только затем допускается новый лидер.
- Нужны HTTPS (или localhost для тестов), Web Locks и BroadcastChannel. Если механизм координации недоступен, обработка блокируется с сообщением, а не запускается независимо.

Границы гарантии: Web Locks и BroadcastChannel действуют внутри одной storage partition. Iframe на другом top-level site может быть изолирован браузером. Рекомендуется размещать Bucket Browser и SignJS на одном origin. Путь внутри бакета не изолирует `localStorage`: тестовый и промышленный контуры на `storage.yandexcloud.net/<bucket>/...` разделяют настройки; для изоляции используйте разные origin.

При обновлении необходимо закрыть или обновить **все** старые вкладки: версии до 1.3.0 не соблюдают блокировку. Между разными серверами/профилями эта защита не действует и не отменяет распределение организаций. Она также не обеспечивает exactly-once для YMQ: повторная доставка, истечение visibility timeout, аварийное закрытие во время загрузки и ошибка DeleteMessage по-прежнему требуют отдельной серверной идемпотентности. Блокировка не перехватывается по таймеру: замороженную ведущую вкладку при необходимости следует закрыть, иначе есть риск параллельной обработки после её пробуждения.

### Промышленный встраиваемый режим

Страница облачного обработчика поддерживает компактный промышленный режим для встраивания в другие интерфейсы. Для его включения используется URL `cloud-sign.html?mode=embedded` (также поддерживается `mode=production`).

В компактном состоянии отображается только круглая кнопка-индикатор:

- серый контур и нейтральный фон — мониторинг выключен или вкладка ожидает лидера/КриптоПро;
- зелёный контур и светло-зелёный фон — мониторинг включён;
- красный контур и светло-красный фон — ошибка обработчика или КриптоПро;
- небольшое покачивание пера — получение сообщений из очереди;
- заметное изменение наклона пера и прорисовка росчерка — обработка и подписание сообщений.

Иконка выполнена в стилистике чернильной гравюры: рука с гусиным пером, лист и чернильница. Рабочая анимация изменяет только изображение, **никогда не меняет цвет фона**. У наблюдателей отображается состояние лидера. При системной настройке `prefers-reduced-motion: reduce` движение отключено.

Проверки: `npm run check`, `npm test`. Автотесты охватывают конкурентный запуск двух вкладок, наблюдение, общую остановку/запуск, передачу лидерства, возврат из BFCache, остановку во время ReceiveMessage/подписи, готовность плагина, отсутствие поддерживаемых API и отсутствие смены цвета в анимациях. Сетевые вызовы и КриптоПро в unit-тестах заменены заглушками; для проверки реальной подписи нужен браузер с установленным плагином и сертификатом.

Нажатие на индикатор разворачивает полный интерфейс в текущем iframe. Кнопка «Свернуть» в верхней части развернутого промышленного интерфейса возвращает компактное представление.

Пример подключения:

```html
<iframe
    id="signjs-widget"
    src="https://storage.yandexcloud.net/20ab2a0c-2726-4ba1-9c7c-7deae82941ff/cloud-sign.html?mode=embedded"
    title="Обработчик электронной подписи"
    width="72"
    height="72"
></iframe>

<script>
window.addEventListener('message', event => {
    const frame = document.getElementById('signjs-widget');
    if (event.origin !== 'https://storage.yandexcloud.net') return;
    if (event.source !== frame.contentWindow) return;
    if (event.data?.type !== 'signjs:layout') return;
    frame.width = event.data.width;
    frame.height = event.data.height;
});
</script>
```

При сворачивании и разворачивании страница отправляет родительскому окну сообщение `signjs:layout` с полями `compact`, `width` и `height`. Сообщение не содержит настроек API, ключей, ИНН или данных подписываемого документа.

## Требования к системе
Для корректной работы на компьютере должны быть установлены:
1.  **КриптоПро CSP** (версия 4.0 и выше).
2.  **КриптоПро ЭЦП Browser Plug-in** (версия 2.0).
3.  **Расширение для браузера** (Яндекс.Браузер, Chrome, Edge или Opera).

## Инструкция по запуску
1. Скачайте файлы проекта: `signJs.html`, `SignJsApp.js`, `style.css`.
2. Поместите библиотеку `cadesplugin_api.js` (от КриптоПро) в ту же папку.
3. Откройте `signJs.html` в браузере.
4. **Важно:** Если вы открываете HTML-файл напрямую с диска (в адресной строке `file:///...`), обязательно зайдите в настройки расширения КриптоПро и включите опцию **«Разрешить открывать ссылки на файлы»**.

## Структура файлов
- `signJs.html` — Структура интерфейса.
- `SignJsApp.js` — Логика взаимодействия с плагином и обработки файлов.
- `style.css` — Стили оформления.
